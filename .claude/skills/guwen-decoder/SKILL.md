# 古文破譯家 (Ancient Text Decoder) — Design Spec

## Standing instruction: keep this file current

The user has explicitly asked that every future requirement, fix, or rule they raise about this feature gets folded into this file **without being asked each time** — they don't want to have to judge what's "worth" documenting themselves. So: after resolving any guwen-decoder request (bug fix, new UX rule, content-authoring decision), update this file in the same session, before considering the task done. Err toward adding — a rule that turns out to be obvious in hindsight costs nothing sitting here; a rule that's missing gets silently violated by a future session with no memory of why it mattered. Keep entries concrete (what broke / what was asked, and the fix), not just abstract principles.

## The word-puzzle format has been deleted

The original model (`src/data/guwen.ts`, `src/pages/GuwenDecode.tsx`, `src/lib/guwenGame.ts`, the `/guwen/:textId` route, the `guwenTexts.map(...)` card list in `GuwenHome.tsx`) is **gone** — deleted in full at the user's explicit instruction when the first text (`wangRongText`, 王戎不取道旁李) was rebuilt from scratch in the evidence-lesson format instead. The user's own words: "原始的舊版 王戎不取道旁李 我們就不要了" followed by an explicit choice of "整個舊版模式的程式碼都刪掉" over just unlinking it from the home page — so this was a considered, confirmed deletion, not an oversight. Any progress recorded under the old lesson id was discarded; the new `wangRongLesson` (id `wang-rong-bu-qu-dao-pang-li`) starts fresh under its own id.

**This feature now has exactly one content format** — the evidence-lesson format below (`src/data/guwenLesson.ts` + `src/pages/GuwenLessonDecode.tsx`). All texts (`wangRongLesson`, `simaGuangLesson`, `keZhouQiuJianLesson`, `shouZhuDaiTuLesson`, `yaMiaoZhuZhangLesson`, `yanErDaoZhongLesson`) live in the single `guwenLessons` array, in that display order. Do not resurrect any word-puzzle-format code, and do not treat old sections of this file describing it (if any survive an incomplete edit) as still accurate — if you find one, it's stale and should be deleted, not followed.

## Evidence-lesson format extensions added for 刻舟求劍 (shared by any future lesson)

The 刻舟求劍 source markdown required three things the format didn't support yet — all added directly to `guwenLesson.ts`/`GuwenLessonDecode.tsx` rather than as one-off lesson-specific code, since a future lesson can reuse any of them:

- **`RevealStep` (`type: 'reveal'`)** — for a multi-word combination the source content explicitly says should *not* get its own multiple-choice question ("不另設整句選擇題", because there's no genuine distractor to offer). Has `intro`, an optional `keys: DecodingKey[]` table, and a single continue button — no `question`/`options`/`correctIndex`/`retryHint` at all, since there's nothing to grade. Still gets its own `id`/`prerequisiteIds`/`decodedWordIds` entry so progress resumes correctly mid-lesson, and still runs through the normal celebration + `explanation` display via `markStepSolved`, called directly from the continue button instead of from `handleSelect`. Every non-reveal render path (`renderOptions`, the retry-hint block, `stepAutoPlayLines`'s question line) had to be re-typed against `Exclude<LessonStep, RevealStep>` or explicitly branched on `step.type !== 'reveal'` — when adding a new step type, grep for every place `LessonStep`'s common quiz fields are accessed unconditionally and check each one still makes sense for the new type. Not every lesson needs this type — 王戎 has none, since its source content never asked for a "don't quiz this" checkpoint.
  - **UPDATE, later session: every single `RevealStep` 刻舟求劍 originally shipped with turned out to be a real UX bug, not a legitimate "nothing to grade" checkpoint — see "刻舟求劍's reveal steps all got converted to graded reconstruction steps" below. As of that fix, `type: 'reveal'` is used by zero lessons in `guwenLessons`.** The type stays in the schema (a genuine no-distractor combination could still arise in a future lesson, and the source doc can explicitly ask for it), but its introduction here for 刻舟求劍 was a misreading of the original source material, not a validated pattern — don't treat "刻舟求劍 used RevealStep six times" as evidence it's commonly the right choice. Default to a real graded step; only reach for `RevealStep` when a source doc explicitly and deliberately says no question should be asked.
- **Three independent, individually-optional closing screens** — `sequenceOrderingClosing?: SequenceOrderingClosing`, `causalChainClosing?: CausalChainClosing`, `evidenceMultiSelectClosing?: EvidenceMultiSelectClosing`, all top-level fields directly on `GuwenLesson`. Shown (in that fixed order, whichever are present) after every `steps` entry is solved, before the final translation unlocks. Not modeled as more `LessonStep`s — their shapes (reorder cards, a graded single-choice reasoning question, multi-select checkboxes) don't fit the common `LessonStepBase` shape at all. Sequence ordering originally used visible up/down buttons because they were expected to be more reliable on mobile. **That decision was superseded by real child feedback in July 2026:** Justin found repeated arrow tapping inconvenient and asked to press, drag, and drop each event card directly. The shared ordering screen now uses a large right-side `⠿` handle with Pointer Events, a lifted-card visual, live target-position feedback, edge auto-scroll, and drop-to-reorder behavior. Keep `touch-action: none` scoped to the handle so the rest of the page still scrolls normally; keep ArrowUp/ArrowDown on the same focusable handle as an accessibility fallback, but do not restore the old visible arrow pair unless the user explicitly asks. Each present screen gets its own id, added to `decodedWordIds` on solve, so a reload mid-closing-sequence resumes at the right one (`closingStage` state, initialized once from `solvedIds` at mount by finding the first not-yet-solved screen in `closingStepsList`, then advanced only by each screen's own explicit continue click via `advanceClosingStage()` — never derived live). **`causalChainClosing` was originally read-only/display-only (no question at all) — this changed; see "The causal-chain closing screen was telling the child the answer" below.**
  - **These three fields were originally a single bundled `closingSequence: { sequenceOrdering, causalChain, evidenceMultiSelect }` object, required all-or-nothing.** That fit 刻舟求劍 (uses all three) but broke when lessons needed different subsets. The approved 2026-07-26 王戎 rewrite uses `sequenceOrderingClosing` plus `evidenceMultiSelectClosing`, with no separate causal screen. `GuwenLessonDecode.tsx` builds `closingStepsList` by checking each field's presence individually (in fixed `ordering → causal → multiselect` priority order), and `advanceClosingStage(fromKind)` walks that actual list. **If you ever add a 4th closing-screen type, follow this same pattern (an independent optional field + presence-checked list-building) rather than reintroducing a bundled/required shape.**
- **`GuwenProgress`/reward plumbing already generalized cleanly**: `allStepsSolved` from the earlier blank-page fix (see below) became `readyForComplete = allStepsSolved && allClosingSolved`, and a lesson with no closing screens at all (司馬光) gets `allClosingSolved = true` vacuously — zero behavior change for existing lessons.

**Two bugs specific to the closing sequence, both the same underlying mistake as the original blank-page bug (a value that changes reactively mid-session is used to gate what's currently displayed) — caught by Playwright, not manual testing:**
1. The "missed completion" safety-net effect (grants the bonus if the child left before clicking "🎉 完成") reacted live to `readyForComplete`. For a lesson *with* a closing sequence, `readyForComplete` naturally becomes true the instant the child finishes the multi-select through the completely normal flow — so the live effect fired immediately, jumping straight to phase `'complete'` before the child ever saw the multi-select's own correct-feedback screen or clicked "開啟白話驗證卷軸" themselves. Fixed by freezing the check to the value present at *mount* only (`useRef(readyForComplete)` — a ref's initializer argument is only used on the first render, which is exactly "was this already fully done before I opened the page").
2. Separately, the JSX condition showing the closing-sequence block itself was gated on `!allClosingSolved` — same bug, different spot: the instant the multi-select's own `recordGuwenWord` call landed, `allClosingSolved` flipped true and the condition went false, yanking the entire block (multi-select's correct-feedback screen included) off-screen. Fixed by gating on `phase === 'steps' && !currentStep && closingStepsList.length > 0` instead (all changed only by explicit user actions or fixed per-lesson data), never on any solved-count-derived boolean.

The general rule these both reconfirm: **anything a step's own successful answer can flip must not also be the thing gating whether that step's own feedback screen stays visible.** Verify this with Playwright by actually completing the last graded item in a sequence and checking the *next* render still shows that item's own feedback — don't just check the eventual end state.

### New patterns established while rebuilding 王戎不取道旁李 (evidence-lesson format)

The user rewrote 王戎 from scratch (GPT-collaborated, "全文核准") in this format after seeing it prove out on 司馬光/刻舟求劍. A few patterns worth carrying into future lessons:

- **A clearly-labeled non-authentic comparison clue is allowed as one of an `evidence` step's two `ClassicalClue`s, when the target is a multi-character phrase prone to a specific misreading and only one genuine real-古籍 comparison exists.** 王戎's 「多子折枝」step pairs a real variant text (《太平御覽》「子壓枝折」) with a second, explicitly fabricated structural-comparison sentence (「葡萄多實壓枝」) — the source markdown itself labels this "仿古結構對照句（非古籍原文）" and requires it be clearly marked, not passed off as real classical language. Implemented by putting that exact warning directly in the clue's `source` field (e.g. `'仿古結構對照句（非古籍原文，僅為比較句子結構而仿寫，不作為歷史語料）'`) — since `source` is the only field rendered as a citation in the UI ("出處：..."), this is the one place the disclosure can live without adding new fields to `ClassicalClue`. **Do not invent a second fabricated clue when a real one would do** — this is a narrow exception for when genuine 古籍 comparison material doesn't exist, not a shortcut to skip sourcing.
- **A single numbered "題" in the source markdown can bundle two distinct question-moments — a general cross-text concept question, then a separate "回到本篇" (back to this text) application question with its own options — and these must become two separate app-level steps, not one.** The schema only supports one `question`/`options`/`correctIndex` per step. 王戎's 之 (題7), 而 (題12), and 必 (題13) each hit this; split into an `evidence` step (the cross-text concept) followed by a `local_inference` or `story_reasoning` step (the application back in this text), linked by `prerequisiteIds`. This redistributes wording across two screens without altering any of it — a legitimate structural adaptation, not a forbidden content change (per the app-implementation-contract's "don't rewrite the content" rule, which is about wording/substance, not about how many screens it's split across).
- **A "作答後必須固定顯示、不得收進可略過或預設摺疊區塊" (must-display, non-collapsible) reminder needs no special UI work** — `currentStep.explanation` (for a graded step) and `evidenceMultiSelectClosing.correctFeedback`/`.finalNote` (for the closing multi-select) are already rendered unconditionally the instant the step is solved, with no collapse/expand affordance anywhere in `GuwenLessonDecode.tsx`. So a mandatory reminder (王戎's 題11 "🧩 這是有證據的推論，不是古文明寫的問句" and 題17's "🔍 明確證據、合理推論和自行想像，不是同一件事" three-layer breakdown) just needs to be **prepended into `explanation`/`finalNote` as plain text** — it will always display, because everything in that field always displays. Don't add a new field or a "pinned note" UI concept for this; the existing always-shown explanation block already satisfies the requirement.
- **The `evidenceMultiSelectClosing` grading is strict-equality per option** (`options.every((opt, i) => opt.correct === multiSelectChoice.has(i))`) — every correct option must be checked AND every incorrect one must be left unchecked, matching a source markdown's "少選/多選都算錯" requirement exactly with no extra code. When authoring the `options` array, don't worry about differentiated "you missed one" vs. "you added an extra" feedback messages unless the source markdown actually supplies distinct text for each case — a single `retryHint` covering both (as 王戎's does: "一項一項回到原文找...") is enough; the per-option ✓/✗ + `detail` breakdown shown after solving already gives the itemized feedback.
- **An approved answer-position audit overrides the legacy answer-balancing adapter.** Set `preserveAuthoredOptionOrder: true` when the master fixes the exact option sequence and correct-position pattern (the 2026-07-26 王戎 rewrite explicitly audits Q1–Q22). Without this flag, `distributeCorrectAnswerPositions()` moves the correct option at module load and silently violates the approved order even though the static lesson object looks correct.
- **Central TTS results may attach an exact pronunciation note to any approved playable field, not only a clue.** Use the shared `PronunciationCue` shape (`displayText` with Zhuyin, `speechText` with Chinese-only wording). `GuwenLesson.introPronunciationCues` and `fullTextPronunciationCues` cover mission/full-text playback; `LessonStep.pronunciationCues` can place notes immediately after `targetSentence`, `intro`, `question`, `retryHint`, or `correctFeedback`; `ClassicalClue.pronunciationCue` covers the classical clue and `unlockedMeaningPronunciationCue` separately covers its playable vernacular line. `stepAutoPlayLines` must interleave each cue directly after the exact affected utterance, and the UI must render it in the same nearby position. Use these fields only for an exact speech unit or approved pronunciation group the user has heard and marked wrong; centrally confirmed-correct candidates must not receive notes. A later real-App replay can disprove an earlier representative-group assumption: in 王戎 Q1, `少年時，嘗過一村院。` pronounced `少（ㄕㄠˋ）` correctly, while the separately replayed exact utterance `陳涉少時，嘗與人傭耕。` pronounced it as third tone. In that case, keep the correct exact utterance unannotated, split the newly confirmed-wrong exact utterance into its own formal audit item, and attach the cue only to that sentence. Do not spread the cue back across the whole former group.
- **Deduplicate a confirmed-wrong cue within each child-facing App page, without deduplicating the audit work.** For the same phrase, reading, and usage on one page, render and speak the cue only after its first occurrence; do not repeat it under the page's later clue gloss, question, feedback, or retry text. A different reading or usage gets its own first cue. A new App page may cue the same reading again at that page's first occurrence. Every exact playable utterance still keeps its own TTS transformation, catalog coverage, fingerprint, and real-device result even when the visible cue is omitted as a same-page duplicate. The approved 2026-07-27 司馬光 revision applies this to Q11 (`中` only after `杖莫能中`, not again after `打不中`) and Q15 (`得活` only once near the first child-facing occurrence, not under every repeat on the same page).
- **If no reliably pronounced homophone exists, do not force a homophone cue.** Keep the visible line in the user-approved standard form with the intended Zhuyin (for example, `得，當作「必須要...」時，念作「ㄉㄟˇ」。`), but make `speechText` describe the tone without saying the ambiguous target character or the unreliable homophone phrase (for example, `這個字，當作必須要的意思時，念第三聲。`). Never send Zhuyin symbols themselves to TTS.
- **Audit generators must disambiguate polyphonic characters by the exact local phrase before assigning a target reading.** A character-level fallback is not enough: for example, `幾乎` uses `幾（ㄐㄧ）`, while quantity questions such as `幾次` use `幾（ㄐㄧˇ）`. When a newly selected representative exposes a missing context branch, fix the generator and the adult pronunciation table before publishing the catalog; never upload a knowingly wrong target reading for the user to judge.
- **Pronoun-reference prompts must keep their candidate set semantically parallel.** In 王戎 Q13 「人問之」, the user corrected the scene-setting list from 「一群孩子、李子和王戎」 to 「一群孩子、王戎和路人」 because the missing referent is the person being asked and all three answer options are people. When the grammatical role already limits the referent to a person, name only people as the live candidates in the prompt; do not include an ineligible object such as 李子.
- **Never paraphrase a famous authentic classical sentence when the original itself is a clean clue.** 王戎 Q18 originally changed 《論語．述而》「三人行，必有我師焉」 into 「三人同行，必有一人可為我師。後果有所學。」; the user rejected this because a highly recognizable original must not be casually rewritten. Keep the exact classical sentence in `ClassicalClue.text`, put any approved explanation or later outcome only in `unlockedMeaning`, and label the source as a real excerpt rather than a mixed AI clue.
- **Some explicitly approved lessons may claim the badge only at the bottom of the verification scroll.** `badgeClaimMode: 'scroll-end'` suppresses the automatic pre-scroll claim dialog; the approved completion copy and evidence boundary show first, then `badgeClaimLabel` is the final primary action. Do not add this mode just because a lesson document includes a badge label. The approved 王戎 lesson deliberately uses the default two-stage ceremony instead: the final answer immediately opens the blue full-screen completion celebration and plays `playGuwenLessonCompleteFanfare()`; that screen remains until the child presses the badge button; the press then plays the distinct `playBadgeAwardSound()` before moving to the completed result page. Combining `launchLessonCeremony()` and `claimBadge()` in one click starts both sound/animation timelines together and lets the badge timer cut the main celebration off, so it must not be used for this flow. Reopening shows the owned badge plus the article-list and next-lesson links.
- **A `ClassicalClue.unlockedMeaning` (the "已破解為" vernacular gloss under a clue) is optional, and must be genuinely omitted — not just left thin — whenever the pattern being tested lives in how the two clues are structurally arranged, not in what any single word means.** A real bug the user caught: 刻舟求劍's 「入水求之」step compares two bare clues, 「方士徐市等入海求神藥」and 「與數人入林求木」, specifically so the child induces the "入X求Y＝進入X，尋找Y" position pattern by comparing them side by side — but both clues had been given a full unlockedMeaning translation ("...一起進入海中，尋找長生不老的仙藥"), which spells out the exact "進入...，尋找..." pattern the question is testing, handing over the answer before the child compares anything. Fixed by making the field `unlockedMeaning?: string` on `ClassicalClue` and deleting the value entirely for those two clues (not leaving an empty string) — `renderClue` in `GuwenLessonDecode.tsx` already conditionally renders the "已破解為" line and its 🔊 button only `{clue.unlockedMeaning && (...)}`, and the auto-play line-builder (`stepAutoPlayLines`) already tolerates a missing gloss by pushing `''` (stripped by its existing `.filter(Boolean)`), so omitting the field needs no other code changes — a clue with no gloss still shows its classical text, its 🔊 button, and its `source` citation, just no vernacular line. **When authoring a new clue pair, ask whether the translation would restate the very pattern/relationship the question asks the child to notice — if so, leave `unlockedMeaning` off, don't write a vaguer-but-still-revealing paraphrase to technically avoid saying the answer.** This is different from the multi-select "must-display" reminder rule above (that rule is about content that MUST show; this one is about content that must NOT show) — keep both in mind when a source markdown's own notes call out a bare-comparison intent.

  **This rule was itself violated twice more in 王戎, both caught by the user later via screenshot, after 刻舟求劍's 入水求之 fix (and this very paragraph) already existed:**
  - 多子折枝's two clues (「子壓枝折」「葡萄多實壓枝」) had `unlockedMeaning` glosses that spelled out "壓著枝條" / "重量壓著枝條" — exactly the "數量多的東西壓在枝上，枝因此彎折" pattern the comparison question tests.
  - 之 (`zhi_evidence` step)'s two clues went further and named the actual referent in parentheses right in the gloss — `「之」（元方）`／`「之」（狼）` — which isn't even a paraphrase-of-the-pattern leak, it's the literal answer to what "之" points to, hard-coded into the display. **The `question` text itself repeated the same leak independently** ("第一條線索要回頭找「元方」，第二條線索要回頭找「狼」") — so removing only the clue's `unlockedMeaning` would not have been enough; check every child-facing field of a step (`intro`, `question`, `retryHint`, clue `unlockedMeaning`) for a leak, not just the one field a previous fix happened to target. `question` was rewritten to describe the comparison generically ("兩條線索裡，「之」後面都沒有再寫出要指的對象是誰") without naming either referent — that part of the fix stands.

    **The first attempt at fixing the clues themselves went too far and had to be corrected — the user caught it via a follow-up screenshot: "不是要把所有的白話翻譯都刪掉，是白話翻譯要保留；但是白話翻譯裡面「之」的後面不要加括號註解之的意思。"** Deleting `unlockedMeaning` entirely (this file's usual fix for this category of leak) was the wrong move here specifically because the target of this step is a *single pronoun* inside an otherwise-safe-to-translate sentence, not the whole clue sentence. Compare with 多子折枝/入水求之, where the *entire* clue text is the pattern being tested — there's no way to translate any part of "子壓枝折" without handing over the "多X壓/折Y" relationship, so full omission is correct there. For 之, everything except the pronoun's referent is safe and helpful to translate (the child still needs to understand "友人慚，下車引" to reason about what "之" must be). **Correct fix: keep `unlockedMeaning`, translate the whole sentence, but represent the pronoun itself as `「之」` untranslated/unresolved** — no parenthetical name, and no added context clause that would name the referent through a back door (the original gloss had continued "元方卻直接走進門，不回頭看" right after the bracket, which — even with the bracket deleted — still answers the question by naming 元方 in the very next clause; that trailing clause isn't part of the quoted classical text itself, so it was dropped entirely, not just the bracket).

    **One more round: the user then asked for a lead-in context bracket to be added back** ("小孩子會不知道之是誰" — without any setup, "友人慚，下車引之" alone gives a child no way to even guess who "友人" is or why they're ashamed) — but still without naming the referent. Final wording: `'（父親的朋友不守時，元方義正言辭地斥責他。）父親的友人感到慚愧，下車拉住了「之」。'` The front-loaded `（...）` context follows this file's own "括號補充資訊放置原則" (context the child needs *before* the sentence goes in front, per 刻舟求劍's authoring rules) and *does* mention 元方 by name — but only as someone who acted earlier (rebuking the friend), not as the answer to "who is 之." The child still has to make the actual inferential leap (元方 is the only other person in the scene, so he's plausibly who the ashamed friend reaches for) — the bracket makes the *scene* legible, it doesn't hand over the *pronoun's referent*. This is the general distinction to hold onto: **naming a person/place as scene-setting context is fine and often necessary (the child can't reason about a scene they don't understand); naming that same person as what a specific pronoun/blank refers to is the leak.** The second clue's gloss still says "狼" for the identical reason — the classical text itself already says 狼 ("劈狼首") — that's faithful translation, not a referent-reveal; nothing about what "之" refers to is resolved in either gloss.

  **General rule this refines: "omit `unlockedMeaning` when it would reveal the pattern" is not always "omit the whole field."** Ask specifically what the child is meant to induce — if it's the meaning of one word/pronoun inside an otherwise-translatable sentence, translate everything else and leave just that one piece as the untranslated classical character (in `「」`, matching `highlightQuoted`'s convention); only omit the entire gloss when the whole clue sentence *is* the pattern being tested, with no safe partial translation possible.

  Both category-A fixes (whole-clue omission) and this category-B fix (partial translation, pronoun left unresolved) start the same way: check every child-facing field of a step (`intro`, `question`, `retryHint`, clue `unlockedMeaning`) for the same leak, don't assume fixing one field caught all of them, and don't assume the previous lesson's fix shape (full omission) is always the right shape for a new occurrence — diagnose what's actually being tested before picking full vs. partial omission.

All lesson-format texts share `AppData.guwenProgress` (`{decodedWordIds, completedAt, timesCompleted?, contentRevision?}` — a lesson's `decodedWordIds` holds solved *step* ids), the shared reward constants (`COIN_PER_GUWEN_WORD`/`STAR_PER_GUWEN_WORD`/`GUWEN_TEXT_COMPLETE_BONUS_*`), and the same pause-capable playback pattern and post-correct celebration sequence. When an approved lesson is replaced in place under the same stable `lessonId`, set a new `GuwenLesson.contentRevision`; reads must ignore an older revision and mutations must start a clean progress record for the new revision, so an old completion cannot unlock or discount the replacement lesson.

### The closing screens need the same "lock circle" + audio treatment as regular steps — this was missed on first ship

A real bug the user caught via screenshots: the three closing screens (sequence-ordering, causal-chain, multi-select) rendered with **no chip row at the top and no audio anywhere** — no auto-played intro, no 🔊 button on any card/node/option. Both were oversights from treating the closing screens as a separate, bolted-on feature rather than continuing the same step-chain UX the rest of the lesson already has.

- **`renderStepChips()` now renders one circle per closing screen too, appended after the word/phrase-step circles** (`totalWordSteps + i + 1` as the label), using the exact same solved/current/locked visual states — solved is amber, the currently-showing closing screen is indigo, anything not reached yet is `🔒`. Closing chips are **display-only, no click-to-review** (unlike solved word-step chips, which open a review panel) — the closing screens don't have a review-panel renderer the way graded steps do, and adding one wasn't asked for. Call `renderStepChips()` in the closing-sequence JSX block, not just the steps block — it was previously only wired into `{phase === 'steps' && currentStep && (...)}`.
- **Every closing screen's intro/explanatory text now auto-plays** the moment that screen appears — a `useEffect` keyed on `[phase, currentStep, allStepsSolved, closingStage]` speaks `sequenceOrderingClosing.intro` / `causalChainClosing.intro` (now followed by `.question` too, since that screen became a graded question — see below) / `evidenceMultiSelectClosing.intro` depending on `closingStage`, mirroring how a regular step's own intro auto-plays. **Per-item content (each ordering card, each causal node, each multi-select option) is deliberately NOT auto-played** — only available via its own 🔊 button — matching the existing rule that corpus/pattern *options* (the things being compared/chosen, not the instructions) are tap-to-listen-only, never part of the auto-play sequence. The user's own framing for this distinction: "前面讀題的地方要念出來... 每一個選項也要有按鈕，雖然不用直接播放。"

### Why the evidence-lesson format exists

The user reviewed the first text after building it and judged several things insufficiently rigorous: corpus "evidence" was often modern Chinese the app made up rather than real classical parallels, and there was no explicit mechanism for reconstructing a multi-word phrase from its solved parts before revealing what it means. They then collaborated with ChatGPT on a full design-and-implementation contract (delivered as a handoff zip: `CLAUDE-TASK.md` + a `design-guwen-decoding` skill package + a complete lesson markdown for 司馬光破甕救友) and had it implemented starting with the *second* text, explicitly as a refinement exercise rather than a retrofit of the first. That handoff package is now installed as the `design-guwen-decoding` skill (`.claude/skills/design-guwen-decoding/`) — **read that skill (and especially its `references/app-implementation-contract.md`) before writing a new evidence-lesson text**, not just this file. Key rules from it, condensed for this app's implementation:
- Cross-text clues must be **real, sourced classical excerpts** — never modern-Chinese sentences, never invented pseudo-classical text. Every `ClassicalClue` needs a traceable `source`.
- Classical text (the lesson's `fullText`, every clue's `text`) is **immutable once approved** — an implementing session must never modernize, paraphrase, reorder, or "improve" it. Modern-Chinese copy (intros, explanations, hints) may be improved, but only via an explicit before/after/reason proposal the user approves — never silently.
- Editorial-only content (segmentation/punctuation analysis for the curriculum designer) must **never** reach child-facing data or screens — keep it in the source markdown/skill files, not in `guwenLesson.ts`.
- A step only becomes available once every id in its `prerequisiteIds` is solved — real dependency resolution (`findCurrentStep` in `GuwenLessonDecode.tsx`), not just "the previous array index," so a lesson with genuine branching would still resolve correctly even though the one text built so far happens to be fully linear.
- The full vernacular translation stays locked (`finalVerification`) until every graded step is solved, and even then requires an explicit "打開白話驗證卷軸" tap — it's a verification scroll the child requests, not something that auto-reveals.

## North Star

> 真正的成就，不是 AI 把古文翻譯給孩子，而是孩子有一天驚訝地發現：「咦？我竟然可以自己讀懂古文了。」

AI is never the teacher handing over an answer — it's a research assistant supplying **corpus evidence** the child compares against. Every design decision in this feature gets checked against one question: *does this make the child do the reasoning, or does it do the reasoning for them?* If a UI element reveals the answer before the child has engaged with evidence, it's wrong, no matter how polished it looks.

Concretely this means:
- Child-facing copy must preserve a **specialist being asked for help** relationship. The AI first says exactly what it still cannot understand after finding the clues, then asks the child—as the 古文破譯家—to judge, trace, or reconstruct it. Do not write the AI as a teacher, commander, or headquarters assigning a quiz; mechanically adding `請` before an instruction is not enough. Opening copy must not say `新任務來了`; it should bring an unread text to the child's expertise. The entry button remains the formal `接受破譯任務`, because a specialist can accept a commission without becoming subordinate to the AI.
- Modern-language translation (`modernTranslation`) is revealed **only after** every word is decoded — it's the reward for solving the puzzle, not the entry point.
- Explanations name the plausible-but-wrong meanings too, and argue for the right one from context — not "here's the definition."
- A puzzle never opens by stating the character's meaning. It opens with evidence to compare.

## Shared pause-capable playback

One generic mechanism used everywhere a *longer* piece of text needs a stop control (full passage, translation, per-word explanation, per-puzzle auto-play) — don't reinvent this per button:

```ts
const [playbackId, setPlaybackId] = useState<string | null>(null);
const [playbackPaused, setPlaybackPaused] = useState(false);

function togglePlayback(id: string, content: string | string[]) {
  const startOrRestart = () => {
    setPlaybackId(id);
    setPlaybackPaused(false);
    const onDone = () => setPlaybackId((cur) => (cur === id ? null : cur));
    Array.isArray(content) ? speakSequence(content, onDone) : speak(content, onDone);
  };
  if (playbackId === id) {
    // Resume restarts from the top rather than calling resumeSpeech() — see the pitfall below.
    playbackPaused ? startOrRestart() : (pauseSpeech(), setPlaybackPaused(true));
  } else {
    startOrRestart();
  }
}
function playbackLabel(id, idleLabel, playingLabel, pausedLabel) {
  return playbackId !== id ? idleLabel : playbackPaused ? pausedLabel : playingLabel;
}
```

Rule of thumb for what needs this vs. a plain one-shot `speak()`: if it's more than ~1 short sentence, or it's something that auto-plays without the user asking, it needs pause. A single corpus option, a single pattern example, a single pattern option, or a single occurrence sentence doesn't (clicking any other 🔊 button just cancels-and-restarts via `speak()`'s own `cancel()` call, which is enough).

`togglePlayback` accepts `content: string | string[]` — pass an array (e.g. `puzzleAutoPlayLines(word)`) when the pause-capable content is actually several lines that must play in strict order (a `pattern` puzzle's target+prompt+examples+question); it internally routes to `speakSequence` instead of `speak`. This is how the same one toggle mechanism covers both a single explanation paragraph and a 6-line puzzle narration — don't build a second toggle function for the sequence case.

For queueing multiple *separate* lines back-to-back where each must fully finish before the next starts (page-entry narration), use `speakSequence(lines, onDone)` instead — it queues real separate utterances so the browser (not a guessed timer) decides when one ends and the next begins.

### Known pitfall: a delayed `speak()` needs its timer tracked, not just its speech cancelled

`scheduleExplanationFor` (called once the post-correct celebration finishes — see above) speaks the explanation via `window.setTimeout(..., 250)` (a short pause after the celebration fires feels better than speaking instantly). If the child clicks "下一個古文字" inside that 250ms window, `cancelSpeech()` alone does nothing — there's no speech playing *yet* to cancel, only a pending timer. The timeout still fires later, once the *next* word's screen is already showing, and hijacks whatever that screen is playing (a real bug the user hit: "我在第二題頁面還聽得到第一題的詳解語音").

The fix, and the general rule: **any `window.setTimeout` that leads to a `speak()` call must have its ID stored in a ref and explicitly cleared by every path that navigates away**, not just have `cancelSpeech()` called on the *already-started* utterance. Here that's `explainTimeoutRef`, cleared by a shared `stopPuzzleSpeech()` helper called from both `handleNextWord` and `handleResetProgress` (both places that change `wordIndex` or otherwise leave the current word behind). The celebration's own roll-up timer (`celebrationTimeoutRef`) follows the identical pattern and is cleared by the same `stopPuzzleSpeech()`. If a future puzzle type or feature adds another delayed-then-speak (or delayed-then-anything) call, route it through the same ref-and-clear pattern rather than trusting `cancelSpeech()` to cover it.

### Known pitfall: `speechSynthesis.resume()` is not reliable — treat "resume" as "restart"

A real bug the user hit: "念全文，唸到一半，我按暫停，它可以停下來，但是我再按一次播放，它不會繼續播放" — pausing worked (`pauseSpeech()`/`window.speechSynthesis.pause()` visibly stopped the audio), but clicking play again produced no sound. This is a known WebSpeech engine issue on some browsers: once paused for more than a moment, the underlying engine silently drops the utterance instead of continuing, and `resume()` becomes a no-op.

**Fix, and the standing rule for every pause-capable control in this feature (both `togglePlayback` and `toggleFullPlayback`, in both `GuwenDecode.tsx` and `GuwenLessonDecode.tsx`):** don't call `resumeSpeech()` on the resume branch at all — call the same start/restart logic used for "begin from idle" instead (re-run `speak()`/`speakSequence()` on the same content from the top). This means resuming always re-plays from the beginning of the current utterance/sequence rather than picking up mid-sentence — a real UX trade-off, but "restarts a sentence or two early" is a far better failure mode than "silently produces nothing," and it's guaranteed to work regardless of which underlying browser bug caused the stall (an explicit pause that won't resume, or Chrome's separate ~15s-continuous-speech auto-stop). `toggleCelebrationPause` (the roll-up celebration's pause button) still calls `resumeSpeech()` for the short praise line — that's a narrower, shorter-lived case that hasn't shown this failure in practice; apply the same restart fix there too if it's ever reported.

### Known pitfall: some characters need a TTS-only pronunciation override, never a text change

A real bug the user hit: "沒應該唸莫，他唸梅" — in "足跌沒水中"/"沒入水中", the child's TTS voice read 沒 as its far-more-common ㄇㄟˊ (méi, "沒有"-style negation) instead of the correct ㄇㄛˋ (mò, "submerged") the classical text needs here. The Web Speech API takes plain text only — no SSML, no phoneme tags — so there's no way to tell the engine "read this character differently" without changing what string it receives.

### Known pitfall (evidence-lesson format): never derive "the current step" fresh from solvedIds every render

`GuwenLessonDecode.tsx`'s first draft computed `currentStep` directly as `findCurrentStep(lesson, solvedIds)` on every render, with no separate state. This looked reasonable but broke the instant the *last* step in a lesson was answered correctly: `recordGuwenWord` adds it to `solvedIds` immediately, so on the very next render `findCurrentStep` finds no unsolved step left and returns `undefined` — which made the entire steps-phase UI (celebration, explanation, and the "🎉 完成" button needed to advance) disappear before the child ever saw it, since it was all gated behind `currentStep &&`. This only surfaces on the *last* step, which made it easy to miss in a quick manual check but was caught immediately by a full Playwright run through all 18 steps.

The fix, and the rule for this format: **the on-screen step is its own piece of state (`activeStepId`), not a live derivation from `solvedIds`** — exactly like `wordIndex` in the older `GuwenDecode.tsx`, which is also independent state rather than computed from `decodedIds`. `activeStepId` only changes when `handleNextStep` explicitly advances it (by calling `findCurrentStep` itself, once, at the moment of navigating away — not on every render). A related off-by-one from the same first draft: the "is this the last step" check was `solvedIds.size + 1 >= totalSteps`, which is wrong because `solvedIds` **already includes** the step just answered by the time that code runs — the correct check is `solvedIds.size >= totalSteps`, with no `+ 1`. Watch for this exact mistake in any future step/word-index-like counter in this feature: always ask "does this collection already include the thing I just did, or not yet?" before writing a boundary condition against it.

### Known pitfall (evidence-lesson format): re-opening a lesson where every step is solved but `completedAt` was never set renders blank

A real user hit this: they solved all 20 steps of 司馬光破甕救友, but instead of clicking the final "🎉 完成！看看整篇文章" button (the only thing that calls `completeGuwenText` and grants the completion bonus), they left via "← 回古文破譯家". Re-opening the lesson showed nothing but the back-link and footer — every phase branch failed to match. Root cause: `phase` initializes from `alreadyComplete` (`Boolean(progress?.completedAt)`) and `solvedIds.size > 0`, with no case for "everything solved but not marked complete" — so it landed on `'steps'`. But `findCurrentStep` (used for the initial `activeStepId`) finds nothing left to solve and returns `undefined`, so `currentStep` is `undefined`, and `{phase === 'steps' && currentStep && (...)}` never renders. None of the other three phase blocks match `'steps'` either. Net result: the whole steps UI silently vanishes, and — worse — the completion bonus (`GUWEN_TEXT_COMPLETE_BONUS_COINS/STARS`) is permanently lost, since nothing else ever calls `completeGuwenText` for that lesson.

Confirmed by seeding `guwenProgress` with all step ids in `decodedWordIds` but no `completedAt` and loading the page directly (Playwright, `justin-chinese-app-v1` in localStorage) — reproduced the exact blank render, then verified the fix below resolves it and grants the coins/stars.

The fix, and the rule for this format: **treat "nothing left to solve" (`solvedIds.size >= lesson.steps.length`) as equivalent to `alreadyComplete` everywhere `phase` is decided**, not just in the live last-step transition (`handleNextStep`, covered above) but also in the *initial* `phase` computation on mount/remount — that's the case the earlier fix didn't cover, since it only handles advancing away from the last step in the same session, not re-opening a lesson later. Additionally, run a one-time effect (guarded by a ref so it can't refire) that calls `completeGuwenText` + `reward(...)` retroactively whenever a lesson is found in this "fully solved but never formally completed" state, so the bonus the child earned isn't silently lost just because they closed the tab one button-press too early. Any new phase-driving boolean in this feature should get the same treatment: ask "can the underlying data reach this state through a path other than the one button that's supposed to cause it?" — here, navigating away was exactly such a path.

### Known pitfall: a step whose `question` repeats as `intro`'s own trailing sentence renders it twice — exact-match was not a general enough fix

A real bug the user hit via screenshot on two different lessons: some `local_inference`/`story_reasoning` steps have no clues panel, so their source-doc content is one continuous sentence that serves as both the scene-setting lead-in *and* the actual question (e.g. 王戎's `zhi_local_qu_li`: "「之」是一支回頭的箭。前文出現的哪個對象，可以接在「取」的後面？" — authored identically into both `intro` and `question`). The JSX rendering `currentStep.intro` and then, right below it, `currentStep.question` had no awareness that these could be the exact same string, so the child saw the identical sentence printed twice in a row.

The first fix pass checked `intro === question` and caught four steps that way. **The user then hit the same visual bug again on a fifth step (`qu_zhi_reuse`) where the fields were *not* exactly equal** — `intro` had real lead-in text *before* a trailing sentence that was copy-pasted as the whole `question`: `intro: '「取之」第二次出現了。「之」又是一支回頭的箭。這次的「取之」確定寫出了哪件事？'` / `question: '這次的「取之」確定寫出了哪件事？'`. Exact-equality missed this because the fields genuinely aren't equal — only `intro`'s *tail* duplicates `question`. A full rescan (checking `intro.trim().endsWith(question.trim())` instead of `===`) turned up four more instances across two lessons that had shipped with this exact shape and gone unnoticed: 王戎's `qu_zhi_reuse` and `bi_reasoning_stage`, 司馬光's `full_text_reconstruction` and `rescue_causal_chain`.

The **audio** side had the identical narrow bug — `stepAutoPlayLines()` originally used `step.question !== step.intro`, so it also missed the suffix case and would have double-read these five steps' shared sentence, not just displayed it twice.

**Fix: generalized from an equality check to a suffix check, in one shared pair of helpers** (`GuwenLessonDecode.tsx`):
- `questionRepeatsIntro(intro, question)` — `intro.trim().endsWith(question.trim())`, true for both the exact-match case (王戎's `zhi_local_qu_li` etc.) and the new lead-in-plus-shared-tail case (`qu_zhi_reuse` etc.). Used by `stepAutoPlayLines()` to decide whether to push `question` as its own spoken line.
- `stepIntroLeadIn(step)` — returns `step.intro` for `reveal` steps (no `question` field to compare against); otherwise, if `questionRepeatsIntro` is true, strips exactly the matching trailing substring and returns whatever lead-in text remains (empty string when the fields are fully equal, nothing left to show). Used everywhere the plain intro paragraph renders — the live step view and `renderReviewPanel()`'s "📖 複習" panel both call this instead of rendering `.intro` raw, so real lead-in text ("「取之」第二次出現了。「之」又是一支回頭的箭。") still displays, just not the repeated final sentence — the bold `question` paragraph elsewhere still carries the question itself exactly once.

**When authoring a new step, don't try to avoid writing `intro` so it ends with the question sentence** — this is a completely natural way for a source doc's App引導語 to read (the setup and the question are one continuous thought), and it's exactly what this fix exists to handle automatically, at both the display and audio layers, for every current and future lesson. No lesson content needs to change to avoid this shape; if you ever add a *third* place that renders a step's `intro` as a standalone paragraph, route it through `stepIntroLeadIn()` too rather than reading `.intro` directly, or the same bug will resurface in that one new spot.

## Rewards

### Reward economy: deliberately above idiom-quiz rate, plus a redo multiplier

The user explicitly asked for this feature's rewards to sit clearly above `COIN_PER_CORRECT`/`STAR_PER_CORRECT` (idiom quiz: 5/2) — "古文...要花大量的時間閱讀、思索、比較" — and for the whole-text completion bonus to be an unusually large, standalone payoff. Current values (`rewards.ts`): `COIN_PER_GUWEN_WORD = 12`, `STAR_PER_GUWEN_WORD = 6` (~2.4x/3x the idiom rate), `GUWEN_TEXT_COMPLETE_BONUS_COINS = 80`, `GUWEN_TEXT_COMPLETE_BONUS_STARS = 40` — the single biggest bonus anywhere in the app, well above `QUIZ_PERFECT_BONUS`/`CHAIN_MILESTONE_BONUS`/`ASSOCIATION_COMPLETE_BONUS` (20/10, 15/8, 20/10). If a third format/text is added and these constants get revisited, keep both of those relative orderings intentional, not just an artifact of when they were tuned.

The user separately asked what happens on a full redo (reset + replay) — currently resetting keeps earned coins/stars but wipes `decodedWordIds`/`completedAt`, so nothing was stopping a full-reward redo loop before this was addressed. Decision made, later refined into a **stepped-down tier per attempt number** rather than one flat redo rate: unlimited redos are always allowed, but only the first 4 attempts pay out at all — `GUWEN_REDO_REWARD_TIERS = [1, 0.6, 0.3, 0.1]` (100%/60%/30%/10% of both the per-word rate and the completion bonus), and the 5th attempt onward earns 0 — replayable forever for practice, just no longer farmable for currency. `guwenRedoMultiplier(timesCompleted)` looks the current attempt number up in that array (`timesCompleted` is already 0-indexed — 0 completions-so-far *is* attempt 1 — so it doubles directly as the array index), falling back to `0` past the array's end. Implementation:
- `GuwenProgress` gained `timesCompleted?: number`, incremented by `recordGuwenTextCompleted` and — critically — **preserved by `resetGuwenProgress`**, which is the whole point: it's the one field that has to survive a reset to tell which attempt number a redo is on. `resetGuwenProgress` now resets to `{ decodedWordIds: [], timesCompleted: prev.timesCompleted ?? 0 }` instead of deleting the progress entry outright.
- `GuwenLessonDecode.tsx` derives `attemptMultiplier` and scales `guwenCoinAmount`/`guwenStarAmount`/`completionCoinBonus`/`completionStarBonus` off it, then uses those — never the raw constants — in every `reward()` call *and* every on-screen number (progress-bar total, celebration roll-up, completion screen, the "全部破解完成再加碼"/reset-confirmation preview text).
- **`attemptMultiplier` must be captured once per run (`useState(() => guwenRedoMultiplier(progress?.timesCompleted ?? 0))`), not derived fresh every render, and only re-set explicitly inside `handleResetProgress`.** This was originally a boolean `isRedo` derived the same way, and the very first implementation computed it live from `progress?.timesCompleted` on every render — which broke the very first completion it was meant to celebrate: `completeGuwenText` bumps `timesCompleted` to 1 as part of *finishing* the first run, so a reactive read would flip to the next tier down the instant that landing state change is reflected, and the just-earned completion screen then displays (though does not actually re-charge) the discounted redo numbers for what was genuinely a first clear. Caught via a Playwright check that compared a live first-time completion (expected 320/160 for the Sima Guang lesson) against a live redo (expected 188/104) — both showed 188/104 before this fix. The reset handler is the only place allowed to update it mid-session, since resetting is the one moment "which attempt number is this" can legitimately change. When the flat-60% design was replaced by the 4-tier one, this same mount-frozen-ref pattern carried over unchanged — only the value being frozen (a multiplier instead of a boolean) and its source function changed.

### Known pitfall: a lesson's displayed "total" must include closing screens, not just `lesson.steps.length`

"當我們的題數有改變的時候，你也要跟着動態改變" — the totals weren't hardcoded numbers, but they were computed as `lesson.steps.length` alone in both `GuwenHome.tsx` and `GuwenLessonDecode.tsx`, which **silently undercounts by however many closing screens the lesson has** (`sequenceOrderingClosing`/`causalChainClosing`/`evidenceMultiSelectClosing` each contribute their own id to `decodedWordIds` on completion, exactly like a step does, so a child correctly expects them to count toward "how many things are in this lesson"). 王戎 was actually the one caught in the screenshot (19 steps + 1 `evidenceMultiSelectClosing` = 20 total, displayed as 19) — not 刻舟求劍 itself, but the same undercount-by-closing-screens bug affects every lesson that has any closing screen at all.

**Fix: `totalGuwenLessonItems(lesson)`** (`guwenLesson.ts`) — `lesson.steps.length` plus a count of whichever of the three closing fields are present. Both `GuwenHome.tsx` (`total = totalGuwenLessonItems(lesson)`) and `GuwenLessonDecode.tsx` (a new `totalGradableItems`, used only for the "已破解 X/Y" display) now call this instead of reading `lesson.steps.length` directly. **`GuwenLessonDecode.tsx` still has a separate `totalSteps = lesson.steps.length` used for a different, legitimately word-steps-only purpose** — deciding whether `handleNextStep`'s button should say "下一道密碼 →" (more word steps left) vs. "繼續 → 最後關卡" (word steps exhausted, hand off to closings) — don't collapse these two into one variable; a "how many word steps are left" check and a "what's the grand total to display" check are different questions that happen to both start from `lesson.steps.length`.

**General rule: never let a lesson's step/closing count live in two places.** Any future display of "how many things are in this lesson" must call `totalGuwenLessonItems()`, not re-derive it locally — that's exactly the kind of value that silently goes stale the next time a lesson's content changes, and the whole point of a shared helper is that fixing it once (as done here) fixes every call site instead of requiring a hunt through the codebase each time a lesson's step count changes again.

## Data persistence

`AppData.guwenProgress: Record<textId, { decodedWordIds: string[]; completedAt?: string; timesCompleted?: number }>`. `decodedWordIds` only ever grows (never records a wrong attempt); `timesCompleted` only ever grows too, and — unlike the other two fields — is not cleared by `resetGuwenProgress` (see the redo-multiplier section above for why). Loading old/cloud data that predates a new `AppData` field must go through `normalizeAppData()` (in `storage.ts`) — applying cloud data directly without it once caused a full white-screen crash when `guwenProgress` was entirely absent from an older snapshot.

## Authoring checklist for a new lesson

**Read `references/lesson-authoring-template.md` first** — a field-by-field markdown→`GuwenLesson` mapping cheatsheet, written after noticing the same section structure (`# 第N題｜破解「X」`, `## 待破解的目標句`, `## 古文線索一/二`, `## 破譯問題`, `## 選項`, `## 正解`, `## 詳解`, etc.) repeat near-identically across four approved source documents (司馬光, 刻舟求劍, 王戎, 守株待兔). It exists to cut rebuild time and token cost on future lessons — the structure is stable enough to template, but several steps still require real judgment (splitting a compound 題, RevealStep-vs-graded-ReconstructionStep, sequenceOrderingClosing-vs-causalChainClosing for a "因果鏈"-titled section that's actually graded) — the template calls these out explicitly rather than papering over them with a rigid parser. Do not attempt to auto-parse a source markdown into `guwenLesson.ts` with a script — the judgment calls are exactly why this stays a documented template, not automation.

1. Pick source material per the established content strategy: short narrative pieces from 世說新語/韓非子/列子/呂氏春秋 — story-driven, one clear point, works cut into 4-8 short clauses. Load the `design-guwen-decoding` skill for the full curriculum-design workflow (choosing clues, the required user-approval checkpoints) before writing any step content — this file only covers how approved content maps into `guwenLesson.ts`.
2. Write `fullText` as one continuous string with real punctuation; split into `sentences: string[]` — **verify by concatenation** (`sentences.join('') === fullText`) before committing, exactly like this:
   ```js
   node -e "console.log(['s1','s2',...].join('') === 'fulltext')"
   ```
3. For each step: pick the right `LessonStepType` (`evidence` for a real cross-text comparison, `reconstruction` when previously-decoded keys get reassembled, `local_inference`/`story_reasoning` when reasoning from context already in this text rather than new cross-text clues, `reveal` only when the source content explicitly says no real question can be asked). If a single numbered "題" in the source markdown bundles a cross-text concept question with a separate "回到本篇" application question, split it into two steps (see the 王戎 之/而/必 pattern above) rather than cramming both into one `question`/`options` pair.
4. Every `ClassicalClue.text` must be a real, sourced classical excerpt — never invented modern-Chinese sentences. A clearly-labeled fabricated structural-comparison sentence is allowed only as a narrow, explicitly-flagged exception (see "A clearly-labeled non-authentic comparison clue" above) — flag it in `source`, never pass it off as real.
5. Write `introSpokenLine`, the `finalVerification` block (`translation`, `comparisonRows`, `completionFeedback`) — the full vernacular translation stays locked until every step (and every present closing screen) is solved.
6. Write explanations per the style rules above (name the plausible-but-wrong readings, argue from evidence, never open with "「X」的意思是..."); re-check every factual claim against `fullText`.
7. Add the new `GuwenLesson` object to the `guwenLessons` array in `guwenLesson.ts` — `GuwenHome.tsx` and routing pick it up automatically, no other wiring needed.
8. `npx tsc -b && npm run build`, then manually verify every step in order plus any closing screens with a temporary Playwright pass (see below) before considering it done.

## Verifying changes (this repo's established pattern)

This repo has no persistent Playwright dependency — install it temporarily, test, uninstall, so it never lingers in `package.json`:
```bash
npm install -D playwright
npm run preview -- --port <free-port> --host 127.0.0.1 &   # or run_in_background
# write a throwaway .mjs script under the repo root using `chromium.launch({ executablePath: '/opt/pw-browsers/chromium' })`
node your_test.mjs
rm your_test.mjs
npm uninstall -D playwright
git diff --stat -- package.json package-lock.json   # must show nothing
```
Useful technique for asserting on speech without real audio: patch `window.SpeechSynthesisUtterance` in `page.addInitScript` to push each utterance's text into a `window.__speechCalls` array, then assert on that array's contents/order after driving the UI.

Known Playwright gotcha in this feature specifically: `page.click('text=開始破譯')` can ambiguously match the intro hint text too (it also contains "開始破譯吧") — use `page.click('button:has-text("開始破譯")')` or another button-scoped selector instead of a bare `text=` selector once multiple elements can contain the same substring.

### `SequenceOrderingClosing.explanation` — added for 守株待兔

守株待兔's graded causal-ordering closing screen (第十八題, titled "完成全文因果鏈" in its source doc — a graded task despite the causal-chain-sounding name, see the authoring template's §2) needed to show an evidence table + assembled causal-chain summary + evidence-boundary paragraph *after* the child gets the order right, not just a one-line `correctFeedback`. `SequenceOrderingClosing` had no field for this (unlike `CausalChainClosing`, which already has `coreSummary`/`evidenceBoundary`) — added an optional `explanation?: string`, rendered in `renderSequenceOrdering()`'s `orderingSolved` block with a pause-capable `togglePlayback` button (same length-based pause-vs-plain-speak rule as everywhere else in this file), right after `correctFeedback` and before the "繼續 →" button. Use this instead of adding a redundant separate `causalChainClosing` screen when a lesson's *graded* sequence-ordering screen is also where the causal-chain summary belongs — 守株待兔 uses `sequenceOrderingClosing` (with `explanation`) + `evidenceMultiSelectClosing`, no `causalChainClosing` at all, the first lesson to combine exactly these two.

### 守株待兔 is a data point: not every lesson needs `RevealStep`

Every one of 守株待兔's "把密碼放回「XYZ」" reconstruction sections has real `選項`/`正解`/`答錯提示` in the source doc — none needed `RevealStep`. Don't assume a new lesson needs `RevealStep` just because 刻舟求劍 used several; check each "組合問題" section's own content for actual options before deciding (see the authoring template's §3).

### Preserve an approved pre-accept full-text opening as one screen

The rewritten 守株待兔 opening explicitly orders three pieces before the child accepts the mission: the AI request, the complete unchanged classical text, then a short readiness line. The shared lesson model now supports `missionOpeningFullText` plus `introClosingLine`; use these when a master file specifies that order, so the accept action enters question 1 directly instead of inserting the legacy extra listening screen. Split blank-line-separated opening and step-intro paragraphs into separate TTS utterances, matching the formal audit catalog's exact playable units.

### 刻舟求劍's six `RevealStep`s all got converted to graded reconstruction steps — a real bug, not a design choice that changed

The user caught this by using the app themselves: at every "把所有密碼鑰匙組合起來" moment in 刻舟求劍, the screen showed the assembled sentence and a single continue button — no question, no options, nothing to actually do. "小孩子讀完這一頁沒有互動，直接按按鈕就跳到下一題了。" This wasn't a deliberate "no genuine distractor exists" case (the one legitimate reason `RevealStep` exists, per the bullet above) — it was simply never re-examined after the format's `RevealStep` type was introduced *for this lesson specifically*. The user had ChatGPT rewrite every one of these moments into a real multiple-choice question and supplied the revised markdown; the fix was applying that content, not inventing new questions from scratch.

**What changed in `guwenLesson.ts`:**
- All six existing `RevealStep`s (`reveal_qi_jian_zhui`, `reveal_ju_qi_qi_zhou`, `reveal_shi_wu_suo_cong_zhui`, `reveal_zhou_zhi_ru_shui`, `reveal_xing_yi`, `reveal_ruo_ci_bu_yi_huo_hu`) changed `type: 'reveal'` → `type: 'reconstruction'` and gained real `question`/`options`/`correctIndex`/`retryHint` fields (their existing `keys` table, `intro`, and most of `explanation` carried over largely unchanged — only the trailing "全部密碼都亮起，看看整句" framing needed rewording into an actual comparison question). Ids, `prerequisiteIds`, and `finalDraftLine` were kept stable.
- A **seventh, brand-new** graded step (`chu_ren_you_she_jiang_zhe`, `type: 'local_inference'`) was added between `she_jiang` and `qi_jian` — the source markdown's revision also added a genuinely new reconstruction moment ("楚人有涉江者") that the original implementation had silently folded into `she_jiang`'s own `finalDraftLine` instead of giving it its own screen. When a revision doc says "N new 選擇題 added," count them against the current step array before assuming they're all 1:1 conversions of existing steps — one may be a real insertion, which means **every `prerequisiteIds` chain after the insertion point needs updating**, and so does `finalVerification.prerequisiteStepIds` (a step easy to forget: it's a flat list generated once, not derived from `steps`, so a newly-inserted step's id must be manually added or the verification scroll can unlock one step early).
- Verified via Playwright by answering all 22 steps in their correct order and confirming each one required a genuine option click (watching for the "下一道密碼 →" button only appearing after `handleSelect` fires, not immediately) — a `RevealStep` that was missed in the conversion would have shown a continue button with no preceding options click, which is exactly what the original bug looked like.

**Lesson for future authoring:** `RevealStep` should be rare enough that seeing several in one lesson is itself worth double-checking against the current source doc, not just assumed correct because it shipped that way before — a step type existing in the schema and being genuinely warranted by the *current* approved content are two different things, and content can be revised after implementation without anyone thinking to re-check which step types are still justified.

## Keep a child-facing reasoning request concise when the options already carry the comparison

When the user explicitly removes a repeated evidence recap from a `story_reasoning` screen, preserve the approved short request and let the options carry the concrete candidate groupings. Do not reinsert the same preceding sentences as a numbered evidence list or add a second question that restates the request. If the approved `intro` already ends with the exact request, set `question` to that same trailing sentence so `questionRepeatsIntro()` and `stepIntroLeadIn()` render and speak it exactly once.

## Keep graded reconstruction screens to one key notice and one direct question

The user found reconstruction screens especially tiring because the same task was often repeated across `intro`, the key table, and `question`: first announcing that the keys were ready, then describing how to combine them, then asking which complete scene was correct. Each sentence looked defensible alone, but the full screen repeated one instruction three times.

For an approved graded reconstruction, preserve this minimal child-facing structure:

1. `下面是我們已經取得的密碼鑰匙。`
2. the existing key table;
3. `「原文句子」最符合下面哪一個選項？`

Let the options carry missing-action, added-detail, direction, order, or evidence-boundary differences. Do not restate those differences before the child answers. Audit the entire rendered and spoken screen as one unit; if removing a sentence leaves the task equally clear and answerable, remove it.

## Keep formal TTS speech-unit IDs stable across copy revisions

Formal pronunciation results are keyed to a `speechUnitId` as well as exact fingerprints. A generator must not assign those IDs only from the current positional order: deleting a heading, shortening an intro, or moving an unchanged utterance would then rename the utterance and orphan a valid device-listening result even though its exact playable text did not change.

When regenerating an existing lesson catalog, first read the previous generated catalog and preserve the prior `speechUnitId` for every unchanged `(questionId, exact playable text)` pair. Only genuinely new or changed utterances receive a new available ID. Fingerprints still decide whether a target result is current; stable IDs prevent unrelated copy edits from invalidating unchanged evidence.

## TTS 實聽台的已聽／未聽規則

- `pending` 視為「還沒聽過」；`correct` 與 `incorrect` 都視為「已經聽過」。
- 實聽台須提供「全部／還沒聽過／已經聽過」篩選，依序播放只播放目前篩選清單。
- 真人備註若明確指出按錯 target、真正錯的是同句另一字，第二階段須保留中央原始紀錄並另做字級歸因校正；不得替其實念對的字加提示。若歸因不明才要求補聽，不可由 agent 猜測。
